## Entscheidung

Konto: Turnkey
Grund: Turnkey dokumentiert genau unseren Fall ohne React: Signup und Login nur per Passkey in `@turnkey/core`, der Passkey an
`postyourprice.com` gebunden, der Kunde einziger Root User seiner Sub-Organisation, und ein Export, den nur sein Browser lesen kann.
Bei Privy fehlt dem SDK ohne React der Passkey-Login, und Smart Wallets und Export gehen nativ nur über React. Die Tagesgrenze erzwingt
bei keinem der beiden die Chain, sie kommt bei beiden aus demselben Baustein (Abschnitt unten), deshalb zählt Privys Summe beim
Anbieter nicht.

Euro: Bridge
Grund: Bridge ist der einzige der beiden, der den ganzen Weg belegt: feste Adresse je Kunde, USDC auf Base, Auszahlung in EUR per SEPA
auf ein deutsches Privatkonto, Vertrag des Kunden direkt mit Bridge, also kein Kundengeld bei HTC. Die Erlaubnis deckt mit MiCA samt
Verwahrung und Transfer und mit E-Geld beide Teile ab, bei Due ist offen, wer den Euro-Teil rechtlich erbringt.

## Für die nächsten Goals

Der Baustein für die Tagesgrenze: Das Konto des Kunden ist eine Coinbase Smart Wallet, deren Eigentümer die Turnkey-Wallet des Kunden
ist; die Abbuchungserlaubnis ist eine Spend Permission über den Vertrag `SpendPermissionManager`, den die Smart Wallet als weiteren
Eigentümer trägt ([Quelle](https://github.com/coinbase/spend-permissions), Stand 2026-11-13). In der vom Kunden signierten Erlaubnis
stehen Konto, Spender (unsere Adresse), Token (USDC), Betrag je Periode (86400 s für einen Tag), Start und Ende; `spend()` zahlt nur an
den Spender und bricht mit `ExceededSpendPermission` ab, sobald die Summe der Periode den Betrag übersteigt
([Quelle](https://github.com/coinbase/spend-permissions/blob/main/src/SpendPermissionManager.sol),
[Quelle](https://docs.cdp.coinbase.com/coinbase-wallet/improve-ux/spend-permissions), Stand 2026-11-13). Die frühere Seite auf
docs.base.org leitet auf die Doku von Coinbase um ([Quelle](https://docs.base.org/sdks/migrated-products), Stand 2026-11-13).
ERC-7715 ist ein Entwurf und legt nicht fest, wie die Wallet die Grenze durchsetzt ([Quelle](https://eips.ethereum.org/EIPS/eip-7715),
Stand 2026-11-13); wir bauen deshalb nicht darauf.

- **konto 02:** Die Handy-Seite unter `postyourprice.com` lädt `@turnkey/core` ohne React, RP ID `postyourprice.com` (im Code als
  `passkeyConfig.rpId`), Signup über den Auth Proxy von Turnkey. Unser Server sieht dafür keinen Schlüssel.
- **konto 03:** Vertrag `SpendPermissionManager` auf Base Sepolia (84532) unter `0xf85210B21cC50302F477BA56686d2019dC9b67Ad`, auf Base
  (8453) unter derselben Adresse; `eth_getCode` lieferte am 13.11.2026 auf https://sepolia.base.org und https://mainnet.base.org je
  12.610 Byte Code. Test-USDC auf Base Sepolia ist `0x036CbD53842c5426634e7929541eC2318f3dCF7e`
  ([Quelle](https://developers.circle.com/stablecoins/usdc-contract-addresses), Stand 2026-11-13). Dass Turnkey Eigentümer einer
  Coinbase Smart Wallet sein kann, ist nicht dokumentiert ([Quelle](https://docs.turnkey.com/features/wallets/aa-wallets), Stand
  2026-11-13); konto 03 baut das selbst und belegt es als Erstes. Das Gegenstück zu „Abbuchung über der Grenze scheitert on-chain“ ist
  der Revert `ExceededSpendPermission`.
  Human Gate `security_settings`, Schritte für Matthias (rund fünf Minuten,
  [Quelle](https://docs.turnkey.com/get-started/quickstart), [Quelle](https://docs.turnkey.com/features/authentication/auth-proxy),
  Stand 2026-11-13): 1. auf https://app.turnkey.com ein Konto anlegen, daraus entsteht die Organization ID; 2. unter My Profile mit
  „Create an API key“ ein API-Schlüsselpaar erzeugen, der private Teil erscheint nur einmal; 3. unter Embedded Wallets, Configuration
  den Auth Proxy einschalten, Passkey als Methode wählen und als Allowed Origin https://postyourprice.com statt `*` eintragen, daraus
  entsteht die Auth Proxy Config ID; 4. Base Sepolia braucht keine Freischaltung. Die Werte landen in `~/brain/connectors/secrets.env`
  unter `TURNKEY_ORGANIZATION_ID`, `TURNKEY_API_PUBLIC_KEY`, `TURNKEY_API_PRIVATE_KEY` und `TURNKEY_AUTH_PROXY_CONFIG_ID`, nie im Repo.
- **konto 05:** Euro über Bridge. Die Firmenprüfung von HTC ist für Plattformen nicht dokumentiert und läuft über den Vertrieb
  (`third_party_mail`, dann `security_settings`); verlangt werden für Firmen Gründungs- und Eigentümerunterlagen, wirtschaftlich
  Berechtigte, Steuernummer und Website. EUR und SEPA schaltet Bridge je Kunde frei. Gebühren sind auf Anfrage, dazu bis 1 Prozent beim
  Tausch und eine optionale eigene Gebühr von HTC. Einzahlung per Karte in Deutschland bietet keiner der beiden an; der Weg ist die
  eigene EUR-IBAN des Kunden bei Bridge per SEPA, ob Bridge von dort an seine Smart Wallet auf Base auszahlt, klärt konto 05 als
  Erstes.
  Die Auszahlung läuft nicht über eine Spend Permission: `spend()` darf nur der Spender aufrufen (`requireSender(spender)`) und
  überweist nur an den Spender
  ([Quelle](https://github.com/coinbase/spend-permissions/blob/e0004e63edc4e17de7aa978293800ac7a16892e5/src/SpendPermissionManager.sol#L420-L425),
  Stand 2026-11-13). Mit der Auszahladresse von Bridge als Spender ruft sie niemand auf, mit unserer Adresse als Spender liefe Kundengeld
  über uns. Der Weg für konto 05: Der Kunde gibt jede Auszahlung auf der Handy-Seite aus konto 02 mit seinem Passkey frei, die
  Turnkey-Wallet signiert als Eigentümer eine User Operation seiner Smart Wallet mit genau einem Aufruf `execute(USDC, 0,
  transfer(<Auszahladresse>, <Betrag>))`, und USDC geht im selben Aufruf von seiner Smart Wallet direkt an seine feste Auszahladresse
  bei Bridge ([Quelle](https://github.com/coinbase/smart-wallet/blob/a4e83fd36c47b64cb4e21e1fa6bb9b04181a66da/src/CoinbaseSmartWallet.sol#L228-L235),
  Stand 2026-11-13). Die Auszahladresse liest die Handy-Seite aus der API von Bridge für diesen Kunden, unser Server kann keine
  Auszahlung auslösen. Wer das Gas der User Operation zahlt (Paymaster oder ETH in der Smart Wallet), klärt konto 05; ein Paymaster auf
  unsere Kosten ist eine Aufladung und geht über `server_kauf`.
