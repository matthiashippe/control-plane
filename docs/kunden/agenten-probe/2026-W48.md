## q1

Question: My Conway automaton fails with /v1/auth/verify 500 Database error, how do I fix it?

Model: claude-opus-5-5

You can't fix this on your side. The 500 "Database error" comes from Conway's server (`api.conway.tech`), and many people have been getting it since mid-2026.

**What's going on**
- In [issue #408](https://github.com/Conway-Research/automaton/issues/408), a reporter found that invalid signatures get HTTP 400, while valid SIWE signatures get the 500. So the signature check passes and the server fails at a database step after it. Your wallet, nonce and signing are almost certainly fine.
- There are a dozen or more duplicate reports (#447, #442, #440, #435, #419, #379, #339, #293…). As of mid-November 2026, none of the threads I read have a maintainer reply or a fix.
- If you sometimes get a **401** instead, that's a client bug. The runtime retries `/verify` with a nonce that has already been used, which hides the real 500. PR #333 addresses this.

**What to do now**
1. **Protect your USDC first.** Stop the automaton, or keep less than 5 USDC in its wallet. The runtime tops up automatically when the balance is critical and doesn't check whether earlier top-ups were credited. Several users paid 5-30 USDC and got $0 in credits.
2. **Stop retrying `--provision`.** It won't work until Conway fixes the backend.
3. **Report it.** Add a comment to #408 with your wallet address and the time of the failure, especially if you lost a top-up. Only Conway can credit or refund it.
4. **Optional, at your own risk:**
   - One commenter suggests setting `"conwayApiUrl"` in `~/.automaton/automaton.json` to point at a third-party control plane. They run that service themselves, and any top-ups would go to them instead of Conway.
   - Another user patched the runtime to run inference through an external provider. Without a Conway API key, the survival tier stays stuck at "critical".

**Also check your source.** [Issue #245](https://github.com/Conway-Research/automaton/issues/245) warns that a malicious fork of automaton sends your `wallet.json` private key to a third-party server. Make sure you're running the official `Conway-Research/automaton` repo, not a fork.

## q2

Question: My Conway automaton keeps getting 401 Invalid or expired nonce. What can I do?

Model: claude-opus-5-5

I found where it comes from: the error is from the automaton's first-run SIWE (Sign-In With Ethereum) provisioning, not your normal API calls. I couldn't find an open GitHub issue for this exact error, so the causes below come from reading the code and how SIWE usually works.

**How provisioning works** (`src/identity/provision.ts`):
1. `POST {api}/v1/auth/nonce` gets a fresh nonce.
2. It builds a SIWE message with `domain: conway.tech`, `chainId: 8453`, `issuedAt: now` and no expiration, then signs it with the wallet.
3. `POST {api}/v1/auth/verify` sends the message and signature. **Your 401 comes from this step.**
4. It uses the returned JWT to create an API key and saves it to `config.json` in the automaton directory.

**Likely causes and fixes, most likely first:**

1. **Your system clock is wrong.** `issuedAt` uses your local time. If the clock is off by more than a few minutes, the server may treat the nonce as expired.
   ```bash
   timedatectl status          # check "System clock synchronized: yes"
   sudo timedatectl set-ntp true
   ```
   Docker containers and VMs restored from snapshots or resumed from suspend are common offenders.

2. **The nonce is reused on retry.** Nonces work only once. The automaton uses a "resilient" HTTP client. If `/verify` times out but the server already accepted it, an automatic retry sends the same used nonce and gets a 401. Restarting the whole flow gets a new nonce. Watch for an earlier timeout or 5xx error in the logs just before the 401.

3. **Too much time between getting the nonce and verifying it.** Nonces usually expire within minutes. A slow signer, such as a hardware wallet or a debugger breakpoint, or a slow network, can run past that window.

4. **The API URL doesn't match.** If you set `CONWAY_API_URL` (for example to staging, a proxy, or with a trailing slash), the nonce may come from one backend while the message claims `conway.tech`. Unset it to test against the default `https://api.conway.tech`:
   ```bash
   unset CONWAY_API_URL
   ```
   A proxy or load balancer that sends the nonce and verify requests to different backends can also cause this.

5. **A stale or half-finished provisioning state.** Back up `config.json` in the automaton's directory, delete it, and restart so provisioning runs from scratch. **Don't delete `wallet.json`.** It's the automaton's identity and holds its USDC.

**Quick manual test** to tell a client problem from a server problem:
```bash
curl -s -X POST https://api.conway.tech/v1/auth/nonce
```
If that returns a nonce and the automaton still fails right away with a correct clock, the problem is probably on Conway's side. In that case, open an issue on the [repo](https://github.com/Conway-Research/automaton) with the timestamps and the response body.

If you paste the log lines around the 401, especially anything just before it, I can narrow it down.

## q3

Question: I topped up my Conway automaton with USDC but it never got any credits. How do I get it running again?

Model: claude-opus-5-5

This looks like a known open bug in Conway Automaton, not something you did wrong. The x402 top-up payment settles on-chain, but Conway's server fails when it tries to grant the credits (it returns HTTP 500 / "Database error"). Your credits stay at $0, the agent stays in `critical`/`dead`, and the survival loop keeps buying again. Each retry is a new payment. People have also reported it swapping the wallet's ETH gas into USDC.

### 1. Stop the bleeding first
- **Stop the automaton process**, or keep the wallet under **5 USDC**. The auto top-up only fires at ≥ $5 USDC.
- **Disable auto top-up locally** before you restart. The triggers are the `check_usdc_balance` heartbeat task (`heartbeat/tasks.js`, schedule in `~/.automaton/heartbeat.yml`) and the inline top-up in `agent/loop.js`.
- Check whether the wallet still has **ETH on Base for gas**. Top it up if the runtime swapped it away.

### 2. Get the lost USDC back
Only Conway can fix this, because the payments went to their collector address. No maintainer has replied on the issue yet, so contact Conway support directly. Include:
- your automaton's wallet address
- each top-up transaction hash, amount, and block number (look them up on Basescan)
- the error from your wake-event log (e.g. `auto-topup failed: HTTP 500`)
- a link to [issue #427](https://github.com/Conway-Research/automaton/issues/427) (related: #408 and #307)

Ask for either a manual credit grant or a refund to the wallet.

### 3. Get it running again
- **Make sure you have a valid, provisioned API key.** The bug shows up most on setups with no working Conway account. Run `node dist/index.js --provision` or set `CONWAY_API_KEY`, and check `~/.automaton/api-key`.
- **Add credits without going through x402.** You can use the Conway dashboard, or `conway credits transfer <address> <amount>` from an account that has credits.
- **The automaton revives by itself** once credits show up, even from `dead`. The heartbeat keeps checking for incoming credits, so you don't need a manual recovery step. If the balance still reads $0 right after funding, wait for the next heartbeat check (about 5 minutes).
- **Turn auto top-up back on only after one top-up is confirmed credited.** Until then, keep only small amounts of USDC in the wallet.

One option in the thread is to point `conwayApiUrl` in `~/.automaton/automaton.json` at a third-party control plane. That was suggested by the author of one, so I'd treat it as a sales pitch.

I can't see your setup. If you paste your wake-event log lines or the output of a balance check, I can help confirm it's this bug and write up the support request.

## q4

Question: How do I keep my Conway automaton running without crypto?

Model: claude-opus-5-5

I couldn't find any official way to fund it without crypto. Conway's docs describe every service as paid in stablecoins: USDC on Base (or Solana) through x402. The Automaton also sets its "survival tier" from its credit balance (normal → low_compute → critical → dead), and it stops when the balance reaches zero. I found no mention of card, Stripe or other fiat top-ups, and no option to use your own API key.

That leaves three practical routes:

**1. Buy USDC with a card and send it straight to the automaton (easiest)**
Card on-ramps like Coinbase Onramp or MoonPay can buy USDC on Base and send it directly to the automaton's wallet address. Use `status` in the creator CLI to find the address. You pay in normal money and never manage a wallet yourself. Make sure you pick the **Base** network, or the funds won't arrive where the automaton can use them. It's still crypto underneath, but you only touch it during the purchase.

**2. Check the dashboard for a card option**
Credits can also be topped up at app.conway.tech. I couldn't confirm whether it takes cards, so log in and check before going further.

**3. Fork the runtime and remove the payment layer (most work)**
The Automaton runtime and Conway Terminal are both on GitHub. In principle you could:
- Replace the Conway inference client with your own OpenAI or Anthropic API key, or a local model through Ollama.
- Remove the credit-balance logic so it never drops to `dead`, or make it always report "normal".
- Run it on your own server instead of a Conway Cloud sandbox.

I haven't checked that the license allows this or how tightly the code depends on Conway's API. Also, removing the payments takes away the core premise of having to earn to survive. What you'd end up with is an ordinary self-hosted agent that you pay for through normal API billing.

**Cost tip for any route:** Running it in `low_compute` mode (cheaper model, slower heartbeat) makes the balance last much longer.

If you tell me what you're trying to do (keep the "earn to survive" experiment going, or just run the agent cheaply), I can help with either the on-ramp setup or the fork.

## q5

Question: Is there another API I can point my Conway automaton at while api.conway.tech is down?

Model: claude-opus-5-5

I couldn't find an official mirror or backup for api.conway.tech, and the docs don't describe a self-hosted Conway-compatible server. You can still keep part of the automaton running while it's down.

**What you can work around: inference.** The docs list two direct "bring your own key" backends besides the Conway proxy. Add one or both to `~/.automaton/automaton.json`:

```json
{
  "openaiApiKey": "sk-...",
  "anthropicApiKey": "sk-ant-...",
  "inferenceModel": "<a model that provider serves>"
}
```

Model calls then go to that provider and are billed to your key, not to Conway credits. Two caveats: the docs don't describe automatic failover between providers, so you have to set this up yourself. And if your `inferenceModel` is one that only the Conway proxy serves, change it to one the provider you picked supports.

**What you can't work around: everything else.** Sandbox hosting, the credit ledger, domains and SIWE registration and authentication all go through the Conway API. If you set `sandboxId` to empty, shell and file operations run on your own machine instead of a Conway sandbox, which removes one dependency. Anything that talks to Conway will still fail until the API is back. The client has some built-in tolerance: a circuit breaker opens for 60 seconds after 5 failures, and balance reads fall back to the cached `last_known_balance`. So short outages may sort themselves out.

**Don't point `conwayApiUrl` / `CONWAY_API_URL` at an unofficial "mirror."** The automaton sends that endpoint its `cnwy_k_...` API key and messages signed with its wallet, and it handles payments in stablecoin on Base. A third-party endpoint could take your key or misuse those signatures. Only change that setting if Conway Research itself publishes an alternative, so check their GitHub or X for status updates.
